# Memory Quality Gates and Observability — Specification

> Status: **implementation-complete / external-native-validation-pending**  
> Classification: **architecture**  
> Runtime scope: **local, in-process, and non-persistent**

This document defines the maintained requirements for Agent Memory quality gates, retrieval evaluation,
bounded diagnostics, Health UI exposure, and service-level test architecture. The implemented design is
described in [plan.md](./plan.md), the execution record is in [tasks.md](./tasks.md), and the complete runtime
metric contract is in [metrics.md](./metrics.md).

## 1. Purpose

Agent Memory depends on SQLite full-text search, vector retrieval, asynchronous extraction and embedding,
scheduled maintenance, and process-owned native resources. A broad unit-test suite is insufficient when a
native binding can silently skip, a retrieval benchmark can exercise toy behavior, or runtime degradation is
not visible through the product's existing diagnostics surface.

The architecture therefore provides three complementary layers of evidence:

1. A CI-owned Native SQLite gate that cannot silently fall back or skip.
2. A deterministic, versioned retrieval evaluation that exercises real SQLite FTS and production fusion.
3. Content-free, bounded runtime diagnostics exposed through the existing Memory Health contract and UI.

These layers share production behavior where correctness depends on it, while test-only vector generation and
metric calculation remain isolated from credentials, providers, and external networks.

## 2. Goals

- Make Native SQLite, FTS, JSON, migration, and storage failures fail the Memory CI job.
- Provide stable commands for portable behavior, deterministic retrieval evaluation, and performance bounds.
- Prevent Memory-owned tests from silently leaving the focused quality gate.
- Measure retrieval quality with versioned fixtures and fixed metric semantics.
- Expose content-free retrieval, extraction, embedding, maintenance, vector, and provider diagnostics.
- Keep every diagnostic data structure bounded in memory and correct across Agent eviction.
- Preserve typed main-to-renderer contracts and avoid new event or legacy IPC paths.
- Replace facade-scale test oracles with service suites and explicit harness capabilities.

## 3. Acceptance Criteria

### AC-1 — Native Memory CI

- The existing `memory-native-validation` job uses the repository-pinned Node 24 and pnpm toolchain.
- The job installs an independent dependency tree and rebuilds the SQLite binding for the Node ABI.
- A smoke step loads the binding, opens encrypted SQLite, creates a table, writes, reads, and closes it.
- Native tests run with `DEEPCHAT_REQUIRE_NATIVE_SQLITE=1`; a missing binding, FTS, JSON, migration harness, or
  unexpected skip must produce a non-zero exit.
- The job runs portable behavior before the Node ABI rebuild, then runs Native storage, retrieval evaluation,
  and performance bounds.
- The retrieval report is uploaded even when a threshold assertion fails.

### AC-2 — Stable Test Scope

- `test:memory:scope` validates a single versioned manifest of behavior, Native, eval, and performance tests.
- `test:memory` runs only portable Memory behavior.
- `test:memory:eval` runs the deterministic retrieval evaluation.
- `test:main:memory-perf` continues to use its dedicated performance configuration.
- Native tests remain workflow-owned and do not have a local package script that could rewrite the Electron
  binding.
- The scope guard rejects missing paths, duplicate ownership, unclassified Memory tests, Native tests in the
  portable set, and exemptions without a non-empty reason.
- Discovery uses explicit ownership paths, filenames, and direct Memory imports rather than broad content
  markers.

### AC-3 — Retrieval Fixture

- The versioned fixture contains at least 200 synthetic corpus rows and 60 queries.
- It covers exact, CJK, path, code, semantic, and mixed retrieval, including cross-Agent distractors and
  multiple relevant IDs.
- The fixture stores text and relevance data, not vectors.
- Corpus and query vectors are generated by the same test-local `deterministic-lexicon-v1` profile with 128
  normalized dimensions.
- The embedder uses NFKC normalization, lowercase ASCII handling, code/path tokens, CJK trigrams, a versioned
  synonym table, stable feature hashing, and L2 normalization.
- The embedder cannot inspect query IDs, subsets, or relevant IDs.
- Gating CJK queries contain at least three consecutive CJK code points after normalization.

### AC-4 — Retrieval Metrics

- The evaluator reports FTS-only, vector-only, and hybrid results.
- Recall@5 is the number of distinct relevant IDs in the first five results divided by the number of relevant
  IDs.
- MRR@10 is the reciprocal rank of the first relevant result within the first ten results.
- nDCG@10 uses binary relevance and the correct ideal DCG for multiple relevant IDs.
- Duplicate result IDs count only at their first position, and queries without relevant IDs are rejected.
- Production distance-to-similarity conversion, similarity threshold, keyword extraction, fusion, and stable
  ordering are used by the evaluator.
- Fixed thresholds gate hybrid results; FTS-only and vector-only remain diagnostic reports.
- A semantic ablation test proves that removing the synonym concept signal reduces semantic retrieval quality.
- The JSON artifact is written before assertions so failed gates retain diagnostic evidence.

### AC-5 — Bounded Content-Free Diagnostics

- Per-Agent state is capped at 64 Agents with a 24-hour TTL and least-recently-used eviction.
- Every distribution retains at most 256 samples in a fixed-capacity ring.
- Percentiles use nearest-rank calculation on a copied and sorted snapshot.
- Process state is independent of Agent retention and stores extraction queue, embedding backlog, vector
  resources, and provider admission data.
- Agent cleanup removes only that Agent's state; presenter disposal clears Agent and process state.
- Recorders accept only numbers, booleans, timestamps, and closed enums.
- Diagnostics never retain query text, memory content, prompts, vectors, provider responses, API keys, SQL,
  stacks, exception messages, or other free text.
- Collector failures are swallowed and cannot change business results.

### AC-6 — Metric Semantics

- Retrieval is segmented by `recall`, `decision`, `search`, and `injection` purpose.
- Every retrieval operation settles exactly once with one terminal outcome and zero or more degradation causes.
- Terminal outcomes are `completed`, `disabled`, `emptyQuery`, `cancelled`, and `failed`.
- Degradation causes are closed and distinguish FTS, vector, embedding, store, and revision failures.
- Embedding success, failure, and FTS-only counters use actual repository state transitions; blocked,
  superseded, fenced, and retryable rows do not create false terminal counts.
- Extraction distinguishes completed, cancelled, and failed chunks; CAS retries increment only immediately
  before a real retry apply.
- Maintenance reports cheap/heavy outcomes, calls, tokens, and every denied budget step.
- Vector warmup distinguishes succeeded, deferred, and failed outcomes.
- Provider diagnostics separate admission decisions from deadline, abort, and late-settle race events.
- Process gauges receive absolute values from resource owners and never aggregate retained Agent state.

### AC-7 — Typed Health Contract and UI

- `MemoryHealthDto.runtime` is required and contains separate `agent` and `process` snapshots.
- Every closed-enum record includes all keys with zero-value defaults.
- An unmanaged or unsampled Agent receives an empty Agent snapshot and the real process snapshot.
- The Health UI displays retrieval p50/p95, degradation counts, extraction queue depth and age, embedding
  backlog, maintenance outcomes, vector current/high-water values, and provider pressure.
- Process-wide data is clearly labeled, provider gauges remain separate from cumulative counters, and missing
  latency samples render as an em dash rather than `0 ms`.
- The UI uses the existing Health refresh path and does not publish a new Memory update event.
- UI output contains no content, SQL, stack, or provider error detail.

### AC-8 — Test Architecture

- Service and infrastructure suites own retrieval, write, embedding, maintenance, conflict, persona, working
  memory, vector, provider, and repository behavior.
- The facade suite retains only composition, public delegation, cross-service workflows, cleanup, disposal,
  and a small regression smoke set.
- Shared test support consists of capability-based repository fragments, controlled promises, clocks,
  diagnostics probes, vector/provider probes, and common fixture builders.
- No centralized `register*` suite registry or production mutable test accessor may be introduced.
- Harness builders must have real service-suite consumers and may not exist only to test themselves.
- Lifecycle, generation, cooldown, cleanup, and race coverage remains behaviorally equivalent after migration.

### AC-9 — Maintained Documentation

- The SDD is self-contained and describes the implemented system without roadmap or dependency narration.
- The metric dictionary records name, unit, scope, sampling owner, capacity, cleanup, and privacy classification.
- The maintained Agent Memory architecture links to this metric dictionary.
- Runtime diagnostics, content-free audit history, and external telemetry are explicitly distinguished.

## 4. Constraints

- Do not add an external analytics SDK, metrics daemon, telemetry endpoint, database table, or versioned
  migration.
- Do not add a real-provider evaluation, credential reader, API key, provider URL, or network request.
- Do not change retrieval scoring, maintenance budgets, provider retry policy, or Memory decision semantics.
- Do not use absolute wall-clock latency as a shared CI threshold.
- Do not create a second Native CI job, smoke implementation, or test manifest.

## 5. Non-Goals

- Product analytics, crash reporting, or cloud telemetry.
- Persistent runtime metric history.
- Real embedding-model quality comparison.
- A new Health polling or update event.
- A new local Native test command.
- Database state-model normalization or legacy status removal.

## 6. Open Questions

None. Interfaces, capacities, metric semantics, privacy boundaries, and validation behavior are fixed by the
implemented architecture.
